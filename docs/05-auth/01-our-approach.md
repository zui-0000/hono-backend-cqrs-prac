# 05-01. このリポジトリの認証方式

方式そのものの解説は [`00-authentication-methods.md`](00-authentication-methods.md) にある。
ここは**このリポジトリが何を選び、何をまだ決めていないか**だけを書く。

> **状態**（2026-08-08）: 契約とテーブルは確定済み。値も決めた。実装はこれから。
> 残る未決は Cookie への移行だけで、それはフロントの構成が決まるまで動かせない。

## 契約が既に決めていること

`schema/src/contexts/auth/` を読むと、**3 つの軸のうち 2 つは決着している**。

| 軸             | 答え                                | 契約のどこに書いてあるか                                    |
| -------------- | ----------------------------------- | ----------------------------------------------------------- |
| ① 状態を持つか | **券ごとに違う**（下記）            | `AccessToken` / `RefreshToken` の doc                       |
| ② どう運ぶか   | **ボディと `Authorization` ヘッダ** | `LoginResponse` / `RefreshRequest` / `@useAuth(BearerAuth)` |
| ③ 券は何枚か   | **2 枚（アクセス + リフレッシュ）** | `LoginResponse` が両方を返す                                |

### アクセストークンは JWT

```tsp
@doc("アクセストークン(JWT想定)。認可に使用する。")
// NOTE: JWT全体の厳密な検証は難しいため、3セグメント形式だけ軽く保証する
@pattern("^[A-Za-z0-9_-]+\\.[A-Za-z0-9_-]+\\.[A-Za-z0-9_-]+$")
```

**3 セグメント形式を pattern で強制している**ので、実装を JWT 以外にはできない。
つまりアクセストークンは**状態を持たない**（検証で DB を引かない）。

### リフレッシュトークンは不透明トークン

```tsp
@doc("リフレッシュトークン(不透明トークン想定)。アクセストークン再発行に使用する。")
// NOTE: 実装都合で形式を変えられるよう、JWTのような強い制約は付けない
```

形式を縛っていない＝**中身に意味を持たせない**。券だけ見ても誰のものか分からず、
サーバ側の記録を引いて初めて意味を持つ。

### そして失効させると宣言している

```tsp
/** ログアウト (要認証。リフレッシュトークンを失効させる) */
```

**「失効させる」と書いた時点で、リフレッシュトークンは保存が必要**になる。
JWT では失効させられないので、この 1 文が方式を決めている。

### 券はボディで受け渡す

```tsp
model LoginResponse {  accessToken: AccessToken;  refreshToken: RefreshToken; }
model RefreshRequest { refreshToken: RefreshToken; }
```

`Set-Cookie` ではなく **JSON のボディ**で返し、更新時もボディで送り返す。
つまり**クライアントの JS が両方の券を保持する**前提。保護対象の操作は
`@useAuth(BearerAuth)` なので `Authorization: Bearer <token>` で送る。

## 採用する構成

契約から導くと、こうなる。

```text
アクセストークン    JWT・短命           → 署名検証だけ。DB を引かない
リフレッシュトークン ランダム文字列・長命 → DB に記録。失効できる。更新時に差し替える
運び方              ボディ + Authorization ヘッダ（Cookie は使わない）
```

[`00-authentication-methods.md`](00-authentication-methods.md#構成の一覧) で言う
**「券を分ける（二段構え）」**にあたる。要件が正反対の 2 つを別の券に割り当てている。

|                    | 求めるもの                    | 割り当て |
| ------------------ | ----------------------------- | -------- |
| 毎リクエストの検証 | **速い**（DB を叩きたくない） | JWT      |
| ログアウト・失効   | **確実に止まる**              | DB 記録  |

毎回走る検証は回数が多いので DB フリーに、失効はログアウト時だけなので DB を叩いてよい。

### 受け入れている代償

**ログアウトは即座には効かない。** アクセストークンは DB を見ないので失効させようがなく、
最大でその寿命ぶん（15 分）は通り続ける（[理由](00-authentication-methods.md#代償ログアウトは即座には効かない)）。

即時性が要るなら寿命を短くするしかないが、そのぶん更新の頻度＝ DB アクセスが増える。
**このリポジトリでは「最大 15 分の遅延」を受け入れる。**
即時失効が要件になったら、そのときアクセストークン側にも失効リストを持つ話になる。

## 保存するもの

アクセストークン用のテーブルは**作らない**（状態を持たないため）。
リフレッシュトークンのぶんだけ要る。

```text
t_refresh_token                                  実装: contexts/auth/infrastructure/
  id          uuid         PK        券 1 枚の識別子（ローテーションのたびに変わる）
  session_id  uuid         INDEX     ログインからログアウトまで不変。JWT の sid はこれ
  token_hash  text         UNIQUE    券のハッシュ。券そのものは保存しない
  user_id     uuid         INDEX     誰のものか（**外部キー制約は張らない**）
  expires_at  timestamptz            長命側の期限
  revoked_at  timestamptz  NULL      失効した時刻
  created_at  timestamptz
```

設計上の注意は 2 つとも [`00-authentication-methods.md`](00-authentication-methods.md#実装で踏みやすい落とし穴) に理由がある。

- **券の採番に `UuidGenerator` を使わない。** id は uuidv7 で統一しているが、
  券に必要なのは逆の性質（予測できないこと）。暗号論的乱数を使う。
- **券そのものではなくハッシュを保存する。** 高エントロピーな乱数なので
  argon2 は不要で、SHA-256 で足りる。

`revoked_at` を NULL 許容にして**行を消さない**のは、
「失効済みの券が使われた」を検出するため。それは盗難のサインなので、
検出したらそのセッションを切る防御につなげられる（範囲の決定は後述）。
下記のローテーションと組み合わせて初めて本領を発揮する
（消してしまうと、再利用が「知らない券」と区別できなくなる）。

`revoked_at` は**時刻**であって真偽値ではない。猶予期間の判定に「いつ失効したか」が要るため。

### `session_id` を別に持つ理由

**券の id とセッションの id は別物**として持つ。JWT の `sid` に載せるのは `session_id` のほう。

券の id を載せると、**古いアクセストークンを持つタブからのログアウトが空振りする**。

```text
1. タブ A が更新   → row1 を失効、row2 を発行。タブ A は accessToken2 (sid=row2)
2. タブ B は accessToken1 (sid=row1) をまだ持っている（JWT なので寿命ぶん生きる）
3. タブ B でログアウト → row1 を失効させる（既に失効済み）
4. row2 は生きたまま。タブ A は更新し続けられる
```

しかも 204 が返るので**成功したように見える**。`session_id` をローテーションを跨いで
据え置けば、どのタブから叩いても同じセッションが落ちる。
「1 セッション = 1 デバイス」という直感とも一致する。

副産物として、[まだ決めていないこと](#まだ決めていないこと) にあった
「行の連鎖を持つか」が**不要になる**。`parent_id` で数珠つなぎにしなくても、
同じ `session_id` を引けば一族がまとめて取れる。

### 外部キー制約を張らない

`user_id` は `t_user.id` を指すが、**Drizzle でも DB でも FK は宣言しない**。

制約を張ると「**user コンテキストの削除が auth の都合で失敗する**」という結合が生まれる。
`deleteUser` の時点で券が残っていれば FK 違反で落ちる、という形で、
コンテキストを分けた意味が消える。参照整合性は DB 制約ではなく
**auth 側の手順**（user が消えたら券も片付ける）で保つ。将来 DB を分けても壊れない。

> `01-database.md` にはかつて「境界を跨ぐ FK も、相手コンテキストの `drizzle-schema.ts` を
> import すれば書ける」と書いていたが、それは `no-cross-context-internals`
> （他コンテキストの `infrastructure/` を禁じる）と**そもそも両立しない**。
> auth が初のコンテキスト跨ぎだったため、今日まで露見しなかった。記述は撤回した。

### テーブル名に所有コンテキストを含めない

`t_auth_refresh_token` ではなく `t_refresh_token`。`t_user_refresh_token` は
**所有者について嘘をつく**ので論外（置き場は `contexts/auth/` で、`user_id` は参照にすぎない）。

`t_auth_` 接頭辞の唯一の価値は「psql の中ではディレクトリ構造が見えない」への対処だが、
それが欲しいなら **Postgres のスキーマ**（`auth.t_refresh_token`）が本筋で、
接頭辞は名前空間を持てない環境での代用品。この DB は既に複数スキーマを使っている
（`drizzle.__drizzle_migrations`）ので、代用品を選ぶ理由が無い。

**見直す引き金**は、テーブルが増えて `\dt` が読みにくくなったとき
（目安: コンテキスト 3 つ・テーブル 10 枚）。そのときも接頭辞ではなくスキーマを検討する。

## 層の割り当て

`hono/jwt` に `sign` / `verify` / `decode` が入っており、**追加の依存は要らない**
（対応アルゴリズムは HS256/384/512、RS・PS・ES 各種、EdDSA）。

ただし **`hono/jwt` は実装**であり、`hono` は presentation の道具。
[`../02-architecture.md`](../02-architecture.md#ポートはそれを要求する層に置く) の規約どおり、
ポートと実装を分ける。

```text
shared/domain/token-issuer.ts              ポート（Context.Tag）
shared/infrastructure/token-issuer-live.ts  実装（hono/jwt を使う）
```

`PasswordHasher` と `PasswordHasherLive`（`Bun.password`）の関係と同じ形。
**Bun を隠したのと同じ理由で Hono を隠す。** これを守らないと
`application-not-to-impl` が落ちるはずなので、ルールが先に教えてくれる。

## user コンテキストとの境界

**初のコンテキスト跨ぎ**になる。ログインには
「メールアドレスで引く」「ハッシュを照合する」「id を券に載せる」の 3 つが要る。

`GetUserQueryService` は使えない。返すのは `name` / `mailAddress` だけで、
**`id` も `hashedPassword` も含まない**（`GET /users/{id}` のための射影として
意図的にそぎ落としてある）。

`UserRepository.findByMailAddress` は必要な情報を返すし、境界ルール上も
参照できてしまう（`no-cross-context-internals` が禁じるのは相手の
`infrastructure` / `presentation` だけ）。**しかし使うべきではない。**
あれは書き込み側のポートで、`create` / `updateProfile` / `deleteById` まで
一緒に握ることになり、「書き込みは所有コンテキストの command を通す」が崩れる。

**user 側に auth 向けの読み取りポートを新設する**のが筋。
DDD の Customer/Supplier（使う側の要求を、供給側が受けて公開する）の初適用になる。

## ローテーションを入れる（決定）

更新のたびにリフレッシュトークンごと差し替え、古いほうを失効させる。
**ただし猶予期間とセットで。**

採る理由は、この構成では**リフレッシュトークンをクライアントの JS が保持する**から。
契約がボディで受け渡す形なので置き場が盗まれやすく、
「盗まれたと気付ける」価値が相対的に高い（[仕組み](00-authentication-methods.md#ローテーション--リフレッシュトークンも入れ替えるか)）。

猶予期間を必ず併せるのは、**並行リクエスト問題**で正規の利用者を締め出さないため。
アクセストークンが切れた瞬間に画面が複数の API を同時に投げると、
先頭以外が「失効済みの券」を提示することになり、**盗難と誤検出される**。

| 対策                                      | どこで       |
| ----------------------------------------- | ------------ |
| 更新を 1 本に絞る（更新中は他を待たせる） | クライアント |
| **差し替え後 N 秒は古い券も受け付ける**   | サーバ       |

> 守るための仕組みが守るべき相手を締め出す——**セキュリティ機能の失敗はだいたいこの形**。
> ローテーションだけ入れて猶予期間を忘れる、というのが典型例。

### 契約の変更（2026-08-08 に適用済み）

`RefreshResponse` はアクセストークンしか返していなかったので、差し替える券を足した。

```tsp
model RefreshResponse {
  accessToken: AccessToken;
  refreshToken: RefreshToken;   // ← 追加
}
```

**項目の追加なのでクライアントは壊れない**（既存の実装は知らない項目を無視する）。
[`../../CLAUDE.md`](../../CLAUDE.md) の基準では破壊的変更にあたらないため `!` は付けない。

## クライアントに求めること

フロントエンドは別リポジトリになるが、**サーバの設計はクライアントの振る舞いを前提にしている**。
とくに猶予期間は「クライアントが並行して更新を投げる」ことを織り込んだ仕組みなので、
何を期待しているかをここに書いておく。

### 更新は 2 段構えにする

```text
土台（正しさ）:  リアクティブ  — 401 が返ったら更新し、元のリクエストを再送する
上乗せ（快適さ）: プロアクティブ — 期限の少し手前で先回りして更新する
```

**タイマーは最適化であって、正しさの土台にはできない。**

| 場面               | タイマーに起きること                                       |
| ------------------ | ---------------------------------------------------------- |
| タブが非アクティブ | ブラウザが `setTimeout` を間引き、**発火が遅れて期限切れ** |
| PC がスリープ      | 寝ている間は進まない。復帰時にはとうに切れている           |
| リロード           | タイマーごと消える                                         |

「切れていたら直す」を土台に置けば、タイマーが裏切っても最終的に必ず復帰する。
逆にリアクティブだけだと**期限切れ直後の 1 リクエストが必ず往復 2 回**になるので、
その体感を消すのがプロアクティブの役目。**役割が違う。**

### 実装で押さえること

1. **タイマーの時刻は JWT から読む。**
   アクセストークンの寿命を別途覚えておく必要はない。
   [JWT は署名されているだけで暗号化されていない](00-authentication-methods.md#3-jwt-は暗号化されていない)ため、
   クライアントが `payload.exp` を読める。**リロード後も手元の券からタイマーを復元できる。**
2. **`exp` ちょうどではなく手前に張る。**
   クライアントとサーバの時計はずれる。30 秒程度の余裕を持たせないと、
   **切れた後に更新へ行く**ことになる。
3. **更新は 1 本にまとめる。**
   更新中のプロミスを 1 つ保持し、更新が必要な呼び出しは全部それを待つ。
   3 本同時に 401 が返っても、実際に飛ぶ更新リクエストは 1 本になる。

### タブを跨ぐぶんはサーバが引き受ける

上記 3 が効くのは**同一タブの中だけ**。タブが 3 枚開いていればタイマーも 3 つあり、
それぞれが更新を投げる。クライアント側のミューテックスでは止められない。

**ここを拾うのがサーバ側の猶予期間**（[ローテーションを入れる](#ローテーションを入れる決定)）。
クライアントに完璧な協調を要求せず、**サーバ側で誤検出を吸収する**という分担にしている。

## 決めた値（2026-08-08）

実装に入る前に、未決だったものを確定させた。

| 論点                 | 決定                                           |
| -------------------- | ---------------------------------------------- |
| アクセストークン     | **15 分**                                      |
| リフレッシュトークン | **2 週間**                                     |
| 猶予期間             | **30 秒**                                      |
| 猶予期間中の応答     | **同じ券をそのまま返す**（発行し直さない）     |
| 署名アルゴリズム     | **HS256**                                      |
| 盗難検出時に切る範囲 | **そのセッションだけ**（全セッションではない） |

**猶予期間は幅の上限（30 秒）を採った。** 短くするほど、タブ跨ぎの並行更新で
正規利用者を締め出す確率が上がる。盗難側のリスクは「30 秒だけ古い券も通る」程度で、
[締め出しのほうが実害が大きい](00-authentication-methods.md#ただしそのままでは正規利用者を締め出す)。

**猶予期間中は同じ券を返す。** 発行し直すと、並行 3 本がそれぞれ新しい行を作り、
クライアントが保持するのは最後の 1 つだけなので**残りがゴミになる**。
`session_id` があるので行の連鎖を追う必要も無い。

**署名は HS256。** 非対称（RS256 等）が要るのは発行と検証が別サーバのとき。
このリポジトリは同一プロセスで完結する。

**盗難検出時はセッション単位で切る。** 失効済みの券が猶予期間の外で使われたら
盗難のサインだが、**猶予期間を入れてもなお誤検出は起こりうる**（時計のズレ、
極端に遅いネットワーク、リトライの重なり）。全セッションを切ると、誤検出のときに
正規利用者が全端末から締め出される。まず狭く切り、必要になったら広げる。

## まだ決めていないこと

| 論点                | 選択肢                                                    | 決める引き金                     |
| ------------------- | --------------------------------------------------------- | -------------------------------- |
| **Cookie への移行** | 現契約はボディ + Bearer。SSR を前に置くなら Cookie が要る | **フロントの構成が決まったとき** |

### Cookie への移行について

現在の契約は **SPA 前提**。`localStorage` や JS のメモリに券を持ち、
ヘッダに載せて送る形になる。

将来 SSR（tanstack-start 等）を前に置くなら話が変わる。
**SSR サーバは `localStorage` を読めない**ので、初回描画で認証付きのデータを取れない
（詳細は [`00-authentication-methods.md`](00-authentication-methods.md#ssr-がある場合は選択肢が狭まる)）。

移行するなら `LoginResponse` からトークンを外して `Set-Cookie` に変え、
`RefreshRequest` のボディも空にすることになる。**`schema/` が変わりクライアントが壊れる**ので、
[`../../CLAUDE.md`](../../CLAUDE.md) の基準どおり破壊的変更マーカー `!` が付く。

**この判断はバックエンド単体では決められない。** フロントの構成が固まってから決める。

## 着手前に片付けること（2026-08-08 に完了）

「`process.env.DATABASE_URL!` の起動時検証」を先送りから昇格させる、と書いていた。
**着手前に片付けた**（[`../04-backlog.md`](../04-backlog.md#processenvdatabase_url-の起動時検証2026-08-08-に解決)）。

当時はこう書いていたが、**前半は誤りだった**。

```text
DB の接続文字列が未設定 → 最初のクエリで失敗する。すぐ気付く   ← 誤り
署名鍵が未設定         → 空の鍵で署名し続ける。エラーは出ない
```

実測したところ、`Bun.sql` は未設定をエラーにせず**既定の接続先へフォールバックする**。
localhost に OS ユーザー名で繋ぎにいくため、設定漏れは「動かない」ではなく
「**別の DB に繋がる**」に化ける。つまり DB 接続文字列も、質としては署名鍵と同類だった。

いまはアプリ側が Effect の `Config`、道具側（`db/migrate.ts` / `drizzle.config.ts`）が
`db/database-url.ts` で、どちらも起動時に落ちる。**`JWT_SECRET` も同じ経路に乗せる** —
`TokenIssuerLive` で `Config.redacted("JWT_SECRET")` を読めば、
`DatabaseLive` と同じく Layer の構築時点で落ちる。

署名鍵が未設定のまま動くと、**誰でも偽造できるトークンを発行しながら正常に見える**。
起動しないほうが圧倒的にましなので、ここは defect（`Layer.orDie`）で構わない。

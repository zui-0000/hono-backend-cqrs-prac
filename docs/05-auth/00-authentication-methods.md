# 05-00. 認証方式の解説

**このドキュメントだけは、他の `docs/` と性質が違う。**

他は「このリポジトリで何をどう決めたか」を書いているが、ここは**一般的な認証方式の知識**を
整理したもの。決定は隣の [`01-our-approach.md`](01-our-approach.md) に書く。

分けた理由は、**知識と決定を混ぜると、決定が読めなくなる**から。
「なぜ JWT を選んだか」を読みたい人に「JWT とは何か」から読ませたくない。
逆に、方式の理解が怪しいまま決定だけ読んでも判断を追えない。だから 2 本に割り、
このフォルダだけディレクトリを切っている（`docs/` は本来フラット）。

---

## なぜ「券」が要るのか

**HTTP はステートレス**で、リクエストごとに完全に独立している。サーバは
「さっきログインした人」を覚えていない。

では毎回パスワードを送るか——だめ。送るたびに漏れる機会が増えるし、サーバは毎回
ハッシュ照合（argon2 等）を回すことになる。あれは**意図的に遅い**処理なので、
全リクエストで走らせるものではない。

そこで **1 回だけ本人確認をして、代わりに引換券を渡す**。以降は券を見せるだけ。
この券をトークンと呼ぶ。

### 認証と認可は別物

|                        | 問い               | 失敗時 |
| ---------------------- | ------------------ | ------ |
| 認証（Authentication） | **あなたは誰か**   | 401    |
| 認可（Authorization）  | **何をしてよいか** | 403    |

HTTP の `401 Unauthorized` は名前に反して「**未認証**」を指す。認可の失敗は 403。
名前が紛らわしいだけで、概念は別。

## 判断は 3 つの独立した軸でできている

認証設計の混乱は、たいてい**この 3 つを 1 つに潰している**ことから来る。

| 軸                 | 問い                     | 選択肢                          |
| ------------------ | ------------------------ | ------------------------------- |
| **① 状態を持つか** | サーバは券の記録を持つか | セッション / JWT                |
| **② どう運ぶか**   | 券をどこに載せるか       | Cookie / `Authorization` ヘッダ |
| **③ 券は何枚か**   | 寿命を分けるか           | 1 枚 / アクセス + リフレッシュ  |

**組み合わせは自由**。「セッション + Cookie」は従来型の Web アプリ、
「JWT + Bearer ヘッダ」は典型的な SPA、という程度の傾向があるだけで、
どの組み合わせも成立する。

## 軸① 状態を持つか — セッション と JWT

いちばん誤解が多いのがここ。**引換券**と**身分証明書**の違いで捉えると分かりやすい。

### セッション ID = 引換券

```text
019fc913-e517-7000-b4b0-6eb2b9b366f0
```

**番号しか書いていない。** 券だけを見ても誰のものか分からず、
サーバ側の台帳（DB / Redis）を引いて初めて意味を持つ。台帳が無ければただの文字列。

### JWT = 身分証明書

```text
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIwMTlmYzkxMy0iLCJleHAiOjE3NTQ0MDB9.署名
                     └─ ここは base64。誰でもデコードして読める
```

デコードすると中身が書いてある。

```json
{ "sub": "019fc913-...", "exp": 1754400000 }
```

最後の署名が**割印**で、サーバの秘密鍵でしか作れない。中身を書き換えると割印が合わなくなる。
だからサーバは**台帳を引かず**、割印を検証して中身をそのまま読む。

### 比較

|                    | セッション                     | JWT                              |
| ------------------ | ------------------------------ | -------------------------------- |
| 券に書いてあるもの | 番号だけ（意味を持たない）     | 中身（誰か・いつまで）           |
| サーバ側の記録     | **要る**                       | **要らない**                     |
| 誰か知る方法       | DB を引く                      | 券を読む                         |
| 失効               | **即座にできる**（記録を消す） | **できない**（期限切れまで有効） |
| 台数を増やすとき   | 記録の共有が要る               | 秘密鍵を配るだけ                 |

**トレードオフの本体は「失効できるか」。**

JWT は状態を持たないのが売りだが、裏返すと盗まれた券を止められない。ログアウトしても
その券は期限まで有効。ここを塞ごうとして失効リストを持ち始めると、
**状態を持たないという利点が薄れる**——というのがよくある行き止まり。

### 「JWT にすればセッションを JWT で表現できる」は誤解

JWT は**セッションを表現する方式ではなく、セッションを不要にする方式**。

> **サーバが覚えておくのをやめて、券自体に書いて偽造できなくする。**

この一文が腑に落ちれば、あとはここから導ける。

## 軸② どう運ぶか — Cookie と Authorization ヘッダ

**どちらが安全か、ではない。危険の種類が入れ替わるだけ。**

|                         | 強い                       | 弱い                     |
| ----------------------- | -------------------------- | ------------------------ |
| `localStorage` + Bearer | CSRF（自動送信されない）   | **XSS**（JS から読める） |
| httpOnly Cookie         | **XSS**（JS から読めない） | CSRF（自動で送られる）   |

Cookie を選ぶなら `SameSite`（`Lax` か `Strict`）と `Secure` の設定が必須。
「Cookie にしたから安全」で止まると CSRF の穴が空いたままになる。

### SSR がある場合は選択肢が狭まる

**SSR サーバは `localStorage` を読めない。** ブラウザの機能なのでサーバに存在しない。

SPA なら API を叩くのは常にブラウザなので、JS が持つトークンをヘッダに載せれば済む。
だが SSR は「サーバが HTML を作るために、サーバから API を叩く」ため、
その時点でトークンがサーバ側に無い。

| 置き場                    | SSR 時に認証付きデータを取れるか              |
| ------------------------- | --------------------------------------------- |
| `localStorage` + Bearer   | **取れない**（サーバから読めない）            |
| メモリ（JS 変数）+ Bearer | **取れない**（同上）                          |
| httpOnly Cookie           | **取れる**（document リクエストに付いてくる） |

localStorage 方式で SSR をやると、初回は未ログイン状態で描画してから JS で取り直す形になり、
**SSR にする意味が薄くなる**。

つまり **SSR を前に置く予定があるかどうかが、②の答えを左右する**。
バックエンド単体では決められない判断。

## 軸③ 券は何枚か — アクセストークンとリフレッシュトークン

### 1 枚では、3 つのうち 2 つしか満たせない

欲しい性質が 3 つある。

1. **検証が速い** — 毎リクエストで DB を引かない
2. **失効できる** — ログアウトが効く
3. **長く使える** — 15 分ごとに再ログインさせられない

**1 枚では、どう選んでも 1 つ諦めることになる。**

| 1 枚の構成                | ①速い | ②失効 | ③長く使える |
| ------------------------- | :---: | :---: | :---------: |
| 長命 JWT（2 週間）        |   ✓   | **✗** |      ✓      |
| 短命 JWT（15 分）         |   ✓   |   ✓   |    **✗**    |
| セッション（不透明 + DB） | **✗** |   ✓   |      ✓      |

長命 JWT は速くて長く使えるが**止められない**。短命 JWT は実質止まるが
**15 分ごとに再ログイン**。セッションは止まって長く使えるが**毎回 DB を引く**。

**2 枚に割ると 3 つとも取れる。** これが二段構えの本当の理由で、
「セキュリティのため」だけではない（①の性能も同時に取りに行っている）。

|                      | 寿命              | いつ使うか       | 露出   | 状態     |
| -------------------- | ----------------- | ---------------- | ------ | -------- |
| アクセストークン     | 短い（15 分程度） | **毎リクエスト** | 多い   | 持たない |
| リフレッシュトークン | 長い（数週間）    | 更新のときだけ   | 少ない | **持つ** |

**露出の多さと寿命を逆相関にする。** よく晒されるものは短く、めったに出さないものは長くてよい。

### 状態は、回数の少ないほうに寄せる

どちらを DB 側にするかは任意ではない。**呼ばれる回数で決まる。**

|                        | 呼ばれる回数                    | DB を引くコスト |
| ---------------------- | ------------------------------- | --------------- |
| アクセストークンの検証 | 毎リクエスト（1 日 数百〜数千） | 効く            |
| リフレッシュ           | 15 分に 1 回                    | 無視できる      |

アクセストークンを DB 参照にしたら、結局セッション方式と同じで①が死ぬ。

### 券ごとに①の答えを変えてよい

3 つの軸が独立している、というのはここで効く。

```text
アクセストークン    = JWT（状態なし・短命）      → 毎回の検証で DB を叩かない
リフレッシュトークン = ランダム文字列 + DB 保存   → 失効させられる
```

**熱いところは状態なし、止めたいところは状態あり。** 要件が正反対の 2 つを、
別々の券に割り当てている。これが二段構えの本当の理由。

「JWT を使い、加えてセッションも持つ」という言い方は、**1 枚の券に両方を適用する**
ように聞こえるので避けたほうがよい。実際には券ごとに答えが違うだけ。

### 構成の一覧

| 構成                       | 検証の速さ   | 失効     | 向いている場面                       |
| -------------------------- | ------------ | -------- | ------------------------------------ |
| セッションのみ             | 毎回 DB      | 即座     | 小規模・単一サーバ。**最もシンプル** |
| JWT のみ                   | 署名検証だけ | できない | 失効が要らない短命 API               |
| **券を分ける（二段構え）** | 速い         | できる   | 一般的な Web アプリ                  |
| JWT + 失効リスト           | ほぼ速い     | できる   | 普段は速く、緊急時だけ止めたい       |

最後の構成も成立する。**期限切れ前に失効させた券だけ**リストに載せるので記録は小さい。
「1 枚で両方」は禁止ではなく、意識してやるなら選択肢。

## 更新はどう動くか

二段構えにすると「では 15 分ごとに何が起きるのか」が次の疑問になる。

### 結局 DB を引くのでは？ — 回数が 2 桁違う

アクセストークンが 15 分で切れるなら、15 分ごとに更新 API を叩き、そこで DB を引く。
**「結局 DB を見る」のは事実。** 減ったのは回数のほう。

|                | 15 分あたりの DB アクセス          |
| -------------- | ---------------------------------- |
| セッション方式 | 200 回（全リクエストで台帳を引く） |
| 二段構え       | **1 回**（更新のときだけ）         |

数字は利用の仕方によるが、**桁が 2 つ違う**という関係は変わらない。
ゼロにしたいのではなく、**200 分の 1 にしたい**というのが狙い。

さらに効くのは**負荷の乗る場所**が変わること。

```text
セッション方式:
  リクエストが増える → DB アクセスが比例して増える
  アプリサーバを増やしても DB は 1 つ → DB が先に詰まる

二段構え:
  リクエストが増える → 署名検証が増えるだけ（各サーバでローカル完結）
  アプリサーバを増やせば増やすだけ捌ける → DB 負荷はほぼ横ばい
```

**アプリサーバは増やせるが DB は簡単に増やせない。** 従量課金のマネージド DB なら、
全リクエストで DB を叩く設計はそのまま請求額に出る。

### 更新すると、古いアクセストークンはどうなるか

**破棄されない。というより、できない。**

JWT はサーバに保存されていないので、**消すべき実体がどこにも無い**。

```text
クライアント側: 変数を新しい券で上書きする → 古い券は「捨てた」ことになる
サーバ側:      何も起きない。コピーを持っている者がいれば期限まで有効
```

**配った券は回収できない。** つまり**更新は失効ではない**。
期限が切れて初めて無効になる。

結果として、更新の直後は**2 枚とも有効な時間**ができる。

```text
0 分 ───────────────── 14 分 ────── 15 分
      券A 有効                       券A 期限切れ
                       券B 発行 ─────────────→ 有効
                       ↑ この 1 分間は A も B も通る
```

これは正常な状態で、実害はない（古いほうもすぐ切れる）。

### 有効期限は「つまみ」

15 分は固定値ではなく、**回すと 2 つが逆方向に動く**調整点。

| アクセストークンの寿命 | DB 負荷 | 失効の効き                       |
| ---------------------- | ------- | -------------------------------- |
| 5 分                   | 増える  | **速い**（最大 5 分で止まる）    |
| 15 分                  | 標準    | 標準                             |
| 60 分                  | 減る    | **遅い**（最大 60 分止まらない） |

### 代償：ログアウトは即座には効かない

上の表の「失効の効き」が意味するのはこれ。

```text
1. ログアウトする      → DB の revoked_at が埋まる
2. リフレッシュトークン → 即座に死ぬ
3. アクセストークン     → まだ生きている。期限まで有効
```

アクセストークンは DB を見ないのだから、**失効させようがない**。
「ログアウトしたのに最大 15 分は API が通る」——これが①の速さと引き換えに払う代償。

短くすれば速く効くが DB 負荷が増える。**つまみを回すと必ずどちらかが悪くなる。**

### いつ更新を叩くか

律儀に 15 分ごとである必要はない。

|                | やり方                                     | 感触                           |
| -------------- | ------------------------------------------ | ------------------------------ |
| リアクティブ   | 401 が返ったら更新して元のリクエストを再送 | 実装が簡単。1 回だけ待たされる |
| プロアクティブ | 期限の少し前に先回りして更新               | 滑らか。タイマー管理が要る     |

どちらも頻度は「15 分に 1 回」に落ち着く。

なお、しばらく離席していた場合はアクセストークンが死んでいるだけで、
リフレッシュトークンが生きていれば 1 回更新して戻れる。これが③の中身。

## ローテーション — リフレッシュトークンも入れ替えるか

更新のたびにリフレッシュトークンごと差し替え、古いほうを失効させるやり方。

**利点は盗難を検出できること。**

```text
1. 攻撃者が盗んだ券で更新 → 新しい券に入れ替わり、古い券は失効
2. 正規の利用者が「古い券」で更新しようとする
3. サーバ: 失効済みの券が使われた = 盗まれている
4. その利用者の券をすべて失効させる
```

ローテーションが無いと、攻撃者と正規利用者が同じ券を使い続けるため、
**盗まれたことに誰も気付けない**。

リフレッシュトークンをクライアントの JS が保持する構成（ボディで受け渡す場合）では、
置き場が盗まれやすいぶん、この検出が効く。

### ただし、そのままでは正規利用者を締め出す

**並行リクエスト問題**という定番の落とし穴がある。

```text
アクセストークンが切れた瞬間、画面が API を 3 本同時に投げた

  A → 401 → 更新 → 成功。券が入れ替わる
  B → 401 → 更新 → 古い券を提示 → 失効済み！
  C → 401 → 更新 → 古い券を提示 → 失効済み！
                    ↓
          サーバ「再利用された = 盗難だ」
                    ↓
          全セッション失効 → 正規利用者が強制ログアウト
```

ネットワーク断でも同じことが起きる。サーバは差し替えて応答したのに
**応答が届かなかった**場合、クライアントは古い券を持ったままになる。

### 対策は 2 つ。両方やる

| 対策                 | どこで       | 中身                                |
| -------------------- | ------------ | ----------------------------------- |
| 更新を 1 本に絞る    | クライアント | 更新中は他のリクエストを待たせる    |
| **猶予期間を設ける** | サーバ       | 差し替え後 N 秒は古い券も受け付ける |

考え方は「**同じ券が繰り返し使われるのは盗難。差し替え直後の数秒は正常な競合**」。
時間で切り分ける。

> **ローテーションは入れる。ただし猶予期間とセットで。**
>
> 「セキュリティ的に良いから」だけで入れると、猶予期間を忘れて
> **正規利用者を締め出すシステム**ができあがる。
> 守るための仕組みが守るべき相手を締め出す——セキュリティ機能の失敗はだいたいこの形。

## すべてを貫く問い

方式の判断は、最終的にこれ 1 つに還元される。

> **盗まれたとき、何ができて、どこまで被害が広がって、どう止められるか。**

- `localStorage` が危ういのは → XSS で読めるから
- Cookie に CSRF 対策が要るのは → 勝手に送られるから
- アクセストークンを短命にするのは → 盗まれている時間を短くするため
- JWT の失効が問題になるのは → 止められないから

**「便利かどうか」ではなく「漏れたときどうなるか」で選ぶ。**
これさえ握っていれば、細かい知識は後から埋まる。

## 実装で踏みやすい落とし穴

### 1. 券の採番に uuidv7 を使わない

id を uuidv7 で統一していると、つい券にも使いたくなる。**向いていない。**

|                        | ランダムなビット数    | 生成時刻   |
| ---------------------- | --------------------- | ---------- |
| uuidv7                 | 74（48 ビットが時刻） | **漏れる** |
| uuidv4                 | 122                   | 漏れない   |
| 暗号論的乱数 32 バイト | 256                   | 漏れない   |

uuidv7 が id に向くのは時刻順に並んでインデックスの局所性がよいからで、
**券に求められるのは逆の性質（予測できないこと）**。券には暗号論的乱数を使う。

### 2. 券をそのまま保存しない

パスワードと同じ理由。DB が漏れたら、そこに書かれた券でなりすませてしまう。
保存するのはハッシュ。

ただし **argon2 は要らない**。argon2 が重いのは「短くて推測しやすい平文」を守るためで、
256 ビットの乱数には総当たりの余地がない。SHA-256 で足りる。

### 3. JWT は暗号化されていない

**署名されているだけ。** 中身は base64 なので誰でも読める。守られているのは
「書き換えられないこと」だけ。

| 入れてよい         | 入れない                         |
| ------------------ | -------------------------------- |
| `sub`（利用者 id） | パスワード・ハッシュ             |
| `exp`（期限）      | メールアドレス・氏名             |
| `iat`（発行時刻）  | 権限の詳細（変更が反映されない） |

中身は最小限にする。プロフィール情報を入れると、変更しても券には古い値が残り続ける。

### 4. 秘密鍵の未設定を起動時に弾く

環境変数から読む秘密鍵は、**未設定でも動いてしまう**のが最悪の失敗モード。

```text
DB の接続文字列が未設定 → 最初のクエリで失敗する。すぐ気付く
署名鍵が未設定         → 空の鍵で署名し続ける。エラーは出ない
```

誰でも偽造できるトークンを発行し続けながら、**正常に動いているように見える**。
起動時に検証して落とすこと。

### 5. 認証失敗のメッセージを書き分けない

「利用者が存在しない」と「パスワードが違う」を書き分けると、
**総当たりで利用者の存在を判定できてしまう**（アカウント列挙）。
どちらも同じ 401・同じ文言で返す。

## 用語の対応
